# record-training-2

把用户自然语言描述的实际训练写入 `train2.0`。月度 Markdown 是正式记录唯一事实源，月度 HTML 和 Dashboard 只做同步展示。

## 适用请求

用户表达以下意图时使用：

- “记录今天的训练”
- “今天练了……”
- “更新 2.0 训练记录”
- “保存今天的 Session Load”

本技能只记录用户实际完成的训练。计划或推荐但未完成的动作不得写入正式记录。

## 固定配置与数据边界

- 12 周周期开始日期：`2026-09-21`
- 默认计划：`train2.0/12周计划安排.md` 的 3 日版
- 唯一训练记录事实源：`train2.0/records/YYYY-MM.md`
- 弱点管理唯一事实源：`train2.0/weakness-tracking.md`
- 能力评估唯一事实源：`train2.0/ability-assessment.md`
- 同步展示：`train2.0/records/YYYY-MM.html`、`train2.0/dashboard.html`
- Dashboard 能力评估是只读镜像；不得通过输入框、按钮或 localStorage 手工创建、修改正式能力成绩
- 不读取、迁移或清理旧 `localStorage` Readiness 与 Session 历史
- 不自动读取或修改 `train1.0/`；用户明确要求完成的弱点初始迁移除外，后续以 2.0 弱点文件独立维护，不再自动同步 1.0
- 同日重复记录必须更新已有条目，不新增重复训练日或重复累计 Session Load

## Step 1：确认日期

1. 用户给出明确日期时，确认日期和星期是否一致。
2. 用户只说“今天”“昨天”等相对日期时，转换成绝对日期并请用户确认。
3. 日期早于 `2026-09-21` 时，提醒该日期早于 2.0 正式周期起点，确认后才能记录。
4. 日期晚于当前日期或明显异常时，先确认，不擅自修正。
5. 日期未确认前不修改任何记录文件。

## Step 2：解析用户已提供的信息

从用户描述中提取以下字段，只保留明确提供的内容：

### 训练基本信息

- 训练日期
- 训练日类型或能力板块
- 训练开始/结束时间（用户提供时记录）
- 训练总时长（分钟）
- 场地和器材（用户提供时记录）
- 每个动作的名称、组数、次数、距离、时长、负荷、RPE、休息时间和备注
- 实际动作顺序
- 完成、删减或临时增加的内容

### 训练负荷与疼痛管理

- Session RPE：0–10
- 训练总时长（分钟）
- Session Load
- 训练前疼痛：0–10、部位、性质
- 训练中最高疼痛：0–10、部位、触发动作
- 训练后疼痛：0–10、部位、性质
- 次日疼痛：仅在用户之后补充时记录，不在当天猜测
- 异常症状：尖锐痛、肿胀、卡顿、不稳、跛行或持续加重

### 当日 Readiness

- 睡眠：1–5
- 当前疲劳：1–5
- 当前酸痛：1–5
- 当前疼痛：0–10
- 当前训练意愿：1–5
- Readiness 得分和绿/黄/红等级

如果当天已通过 `recommend-training-2` 写入 Readiness，读取并复用该日原始值；不得重新推断。用户明确表示状态发生变化时，记录训练前最终值，并在备注中说明更新。

## Step 3：检查必要信息并引导补充

正式记录至少需要：

1. 日期。
2. 实际训练内容：至少一个动作、项目或明确的恢复训练内容。
3. 对每个项目可确认的组次、次数、距离或时长；若用户确实记不清，可明确记为“未记录”。
4. 训练总时长（分钟）。
5. Session RPE（0–10）。
6. 训练前和训练后疼痛（0–10）；疼痛大于 0 时补充部位，能回忆时补充性质。
7. 当日五项 Readiness；若当天已有正式条目则不重复询问。

引导规则：

- 一次最多询问 2–3 项，收到回答后再检查剩余缺口。
- 优先询问会影响 Session Load 和安全判断的字段：总时长、Session RPE、疼痛。
- 用户明确说“记不清”“没记录”时停止追问该项，保留为未记录。
- 不要求用户为没有发生的阶段补数据。
- 输入超出量表范围时请用户重新确认，不能自动截断。
- 用户出现异常症状时先提醒停止相关训练并建议专业评估，再继续做忠实记录；不得给出医学诊断。

## Step 4：计算派生数据

### Session Load

仅在训练总时长和 Session RPE 都由用户确认后计算：

```text
Session Load = 训练总时长（分钟）× Session RPE
```

- 结果单位记为 AU。
- 任一输入缺失时 Session Load 写“未计算”，不得估算。
- 同一天有多个训练段时：分别记录每段时长和 RPE；总 Session Load 为各段 `时长 × RPE` 之和。若用户只提供整日总时长和一个 Session RPE，则只计算一个整日值。

### Readiness

当五项原始值齐全而当天尚无已计算结果时，使用与 `recommend-training-2` 完全相同的公式：

```text
Readiness = round(20 × (
  睡眠 / 5
  + (6 - 疲劳) / 5
  + (6 - 酸痛) / 5
  + (10 - 疼痛) / 10
  + 训练意愿 / 5
))
```

分级：

- 绿色：分数 ≥75 且疼痛 ≤2，且无异常症状。
- 黄色：分数 60–74，或疼痛 3–4，且无异常症状。
- 红色：分数 <60，或疼痛 ≥5，或存在异常症状。

疼痛覆盖总分。Readiness 用于记录当日状态，不得根据训练完成情况反向篡改。

### 周期位置

以 `2026-09-21` 为第 1 周第 1 天，计算并记录第几周及 `12周计划安排.md` 中对应阶段。超出 12 周时只记录日期，并标记“周期待确认”，不擅自循环。

## Step 5：读取上下文并做客观总结

更新前读取：

1. `train2.0/records/YYYY-MM.md` 当前月份记录。
2. `train2.0/records/` 最近 3 个训练周的月度 Markdown。
3. `train2.0/12周计划安排.md`。
4. `train2.0/训练周期安排建议.md`。
5. `train2.0/篮球运动训练理念.md`。
6. `train2.0/篮球运动员版动作库 2.0.md`。
7. `train2.0/weakness-tracking.md`，用于核对已有弱点、避免重复项并维护状态。
8. `train2.0/ability-assessment.md`，用于核对已有动作、比较口径、当前最佳结果和更新时间。
9. `train2.0/dashboard.html` 和当月 HTML，用于同步现有结构。

总结只可基于：

- 用户明确反馈；
- 本次实际数据；
- 同一动作的历史组次、负荷、RPE 或动作质量对比；
- 周期计划中明确的目标和负荷规则。

可以指出客观差异，例如“总时长较上次增加 10 分钟”；不得推断用户未描述的肌肉感受、技术问题、疼痛原因或恢复状态。

### 弱点识别与维护

每次记录训练时，必须把本次用户反馈和客观数据与 `train2.0/weakness-tracking.md` 逐项比对，并主动维护该文件：

1. **可以识别为弱点的证据**：用户明确指出的技术短板；动作质量问题；左右侧差异；活动度、稳定性、力量、速度、体能或篮球技能测试短板；在多次记录中重复出现且有数据支持的问题。
2. **新增弱点**：证据能直接支持且现有表格没有同义条目时，新增“弱点项、板块、发现日期、当前状态、目标、备注”。发现日期使用首次有证据的训练日期，状态默认“待改善”。目标只能描述可观察的改善结果，不得编造数值目标。
3. **更新已有弱点**：同一问题再次出现时，在原条目备注中追加日期和新证据；有明确改善数据时更新状态或备注，不新增同义重复项。
4. **不得错误归类**：一次疼痛、头晕、疲劳或其他症状仍记录在疼痛/异常症状与后续关注中；除非记录直接显示相关能力短板，否则不得自动转写为弱点或推断医学原因。
5. **不得擅自关闭**：一次训练未提及某弱点不代表已经改善。只有用户反馈、复测或连续训练数据提供明确改善证据时，才能把状态改为“改善中”或“已改善”。
6. **同步展示**：任何弱点新增、状态或备注更新，都必须同步更新 `train2.0/dashboard.html` 的弱点管理模块；Dashboard 必须完整镜像弱点文件的六个字段，不得只展示缩写标签或另一套写死数据。

### 能力评估提取与维护

每次正式训练写入月度 Markdown 后，必须从本次实际完成数据中提取能力评估候选，并与 `train2.0/ability-assessment.md` 逐项比较：

1. **候选来源**：只接受 `train2.0/records/YYYY-MM.md` 中已完成动作的真实结果。推荐计划、未完成动作、目标剂量、弱点描述、旧 localStorage、用户未确认的数据均不得进入能力评估。
2. **最低数据要求**：候选必须同时包含动作名称、明确指标、数值、单位或完整成绩口径，以及训练日期。只有计划组次而没有测量结果、负荷、固定条件产出或明确质量评分的动作不创建条目；例如只有 `CMJ 3×3` 而没有跳高，不能建立 CMJ 高度成绩。
3. **首次创建**：同动作、同变式和同指标尚无条目时，首次有效结果同时作为基线与当前最佳；写入能力分类、动作、评估指标、当前最佳表现、比较条件与方向、首次记录日期、最佳结果日期、更新时间和来源训练记录。
4. **可比性门槛**：只有动作、变式、侧别、器材口径、单位和测试条件一致的数据才能比较。条件不同或指标此升彼降而无法客观判断时，保留原结果，不换算、不覆盖，也不创建一个伪装成同指标的重复条目。
5. **明确方向指标**：距离、高度、次数、固定时长命中数和质量评分以更高为优；冲刺、敏捷等完成时间以更低为优。投篮命中率必须同时记录命中数和出手数，不得由命中数单独推导。
6. **负重动作比较**：仅当负荷和完成量均不下降且至少一项提高时，判定为更好；负荷与完成量完全相同时，较低 RPE 可作为进步。负荷提高但次数下降、组数提高但负荷下降等混合变化一律视为不可比较，除非正式评估文件已为该动作定义其他用户确认的比较规则。
7. **更新规则**：候选严格优于当前最佳时，才更新最佳表现、最佳结果日期、更新时间和来源；没有超过时不修改条目，也不刷新更新时间。首次记录日期永远保留。
8. **同日补充与纠错**：同日重复保存时更新原候选，不新增重复能力条目。若正式训练记录被纠正，必须基于全部正式历史重新计算对应动作；数据纠错可以降低或移除原最佳值，不受“仅更优更新”限制。
9. **禁止混入**：疼痛、头晕、Readiness、Session Load 或单独的 RPE 不是动作能力成绩。定性动作问题进入训练总结或弱点追踪，不得伪造成数值评估。
10. **同步展示**：`train2.0/dashboard.html` 的能力评估必须完整只读镜像正式评估文件，只展示已有真实条目，并显示首次记录日期、最佳结果日期和更新时间；不得恢复手工保存按钮、输入框或 localStorage 数据。

## Step 6：更新月度 Markdown

目标：`train2.0/records/YYYY-MM.md`。

### 日历条目

- 找到对应日期行，填入训练类型并链接 `#训练详情-YYYY-MM-DD`。
- 若只有 Readiness 尚未训练，标记“Readiness 已记录”，不得显示为已完成训练。
- 同日已有记录时原位更新，不新增重复日期。
- 休息日使用 `🧘`，不计入训练天数或负荷。

### 详情结构

```markdown
### 训练详情 YYYY-MM-DD

**周期位置**：第 N 周 · 阶段名称 · 3 日版槽位
**训练板块**：按实际内容
**训练状态**：已完成 / 部分完成 / 恢复日

#### 当日 Readiness

| 睡眠 | 疲劳 | 酸痛 | 疼痛 | 训练意愿 | 得分 | 等级 |
|------|------|------|------|----------|------|------|
| N/5 | N/5 | N/5 | N/10 | N/5 | N/100 | 绿色/黄色/红色 |

疼痛备注：部位、性质或“无”。

#### 训练内容

| 顺序 | 模块 | 动作/项目 | 组数×次数/距离/时长 | 负荷 | RPE | 备注 |
|------|------|-----------|---------------------|------|-----|------|
| 1 | 用户数据 | 用户数据 | 用户数据或未记录 | 用户数据或未记录 | 用户数据或未记录 | 用户反馈 |

#### 训练负荷与疼痛管理

| 项目 | 数据 |
|------|------|
| 训练总时长 | N 分钟 |
| Session RPE | N/10 |
| Session Load | N AU 或未计算 |
| 训练前疼痛 | N/10 · 部位/性质 |
| 训练中最高疼痛 | N/10 · 触发动作，或未记录 |
| 训练后疼痛 | N/10 · 部位/性质 |
| 次日疼痛 | 待补充或用户数据 |

#### 实际完成情况

- 只写用户明确说明的完成、删减、替换和临时增加内容。

#### 训练总结

- 记录与历史或周期目标之间可由数据支持的客观比较。
- 没有足够证据时写“暂无足够历史数据进行比较”。

#### 后续关注

- 只记录用户反馈或数据直接显示的待观察事项。
```

只写有数据的可选字段。不得为了填满模板生成内容。

### 新月份处理

如果文件不存在：

1. 创建完整月份日历，以周一为每周起始。
2. 每个日期只出现一次。
3. 预留训练详情区域。
4. 不复制 1.0 或旧 localStorage 数据。
5. 沿用当时已存在的 2.0 月度 Markdown 结构；首月结构由实施计划步骤 7 建立。在步骤 7 完成前，如目标文件不存在，应暂停并告知用户先初始化月度记录，不得自行创建另一套格式。

## Step 7：同步月度 HTML

目标：`train2.0/records/YYYY-MM.html`。

仅当对应月度 HTML 已按项目模板存在时同步：

1. 更新 `trainingDays` 中对应日期的标签和状态。
2. 写入或更新 `id="detail-YYYY-MM-DD"` 的详情区块。
3. Readiness、动作、组次、负荷、疼痛、Session Load、总结与 Markdown 完全一致。
4. 详情展示必须沿用 2.0 月度页现有的完整分区风格，并参考 `train1.0/records/2026-09.html` 的信息层次：
   - 顶部使用训练板块、周期位置、Session RPE 和 Session Load 标签概括本次训练。
   - Readiness 使用独立表格，不把全部信息压缩成一排 pill。
   - 按实际顺序拆分为准备/防伤、爆发或速度、力量与辅助、核心、篮球技巧、整理等存在数据的阶段；每个阶段用表格展示项目、组次/时长、负荷、RPE 和反馈。
   - 使用独立的“训练负荷与疼痛反馈”“训练总结”“后续关注”和“待补充”区块；有数据时必须展示，不能把整次训练压缩成数段正文。
   - 总结必须包含实际完成内容、周期计划对照和有依据的历史比较；历史不足时明确说明，不得省略总结或编造评分。
   - 后续关注只列用户反馈、疼痛/异常症状和弱点文件中有直接证据支持的事项。
5. 日历链接必须动态指向对应日期，不得硬编码为单一日期。
6. 休息日写入 `REST_DAYS`，使用休息样式、不可点击且不使用训练日高亮。
7. 同日更新原区块，不能生成重复 ID。
8. 保持桌面端信息密度和移动端响应式可读性；动作明细表在窄屏可横向滚动，反馈卡片应自动降为两列或单列。

如果 HTML 模板尚不存在，先完成 Markdown 更新并明确报告“月度 HTML 尚未初始化，未完成展示同步”；不得复制 1.0 页面后悄悄形成未批准结构。

- 同一天重复更新时替换原值，不重复增加训练天数或 Session Load。

## Step 9：一致性核对

完成前逐项核对：

- 日期、周期周次和训练类型一致。
- 五项 Readiness 原始值、得分和等级一致。
- 动作、顺序、组次、负荷、RPE 和备注一致。
- 总时长、Session RPE、Session Load 计算一致。
- 训练前、中、后疼痛和部位一致。
- 同日只有一个日历条目、一个 Markdown 详情和一个 HTML ID。
- 月度统计不包含休息日，且同日更新没有重复累计。
- Dashboard 链接指向正确月份和日期。
- 本次记录中可直接识别的新弱点已新增，已有弱点的新证据或状态已原位更新，没有同义重复项。
- `weakness-tracking.md` 与 Dashboard 弱点管理模块六个字段逐项一致。
- 本次具备真实、完整且可比较结果的动作已进入能力评估候选；缺少测量结果或条件不一致的动作未被强行比较。
- `ability-assessment.md` 与 Dashboard 能力评估逐项一致，首次日期、最佳结果日期、更新时间和来源完整，且无手工输入或 localStorage 依赖。
- 未超过既有最佳值的动作没有覆盖最佳表现或刷新更新时间。
- 月度 HTML 使用分阶段动作表、负荷疼痛反馈、训练总结和后续关注的完整详情结构，而不是简化正文卡片。
- 执行 `git diff --check`。

## 禁止行为

1. 禁止编造动作、组次、负重、RPE、疼痛、Readiness、感受或技术表现。
2. 禁止把推荐但未完成的动作写入训练记录。
3. 禁止在时长或 Session RPE 缺失时估算 Session Load。
4. 禁止从旧 `localStorage` 或 `train1.0/` 补齐 2.0 历史。
5. 禁止覆盖或删除其他日期的历史记录。
6. 禁止把同一天重复保存为多个训练日或重复累计负荷。
7. 禁止在月度模板或 Dashboard 模块尚未实施时发明临时数据结构。
8. 禁止将疼痛原因写成未经专业评估的医学诊断。
9. 禁止把只有计划组次、定性反馈或缺少测量值的动作伪造成能力成绩。
10. 禁止用不可比条件覆盖最佳表现，或在成绩未提高时刷新能力评估更新时间。
11. 禁止从输入框、按钮、旧 localStorage、推荐计划或未完成动作创建正式能力评估。
